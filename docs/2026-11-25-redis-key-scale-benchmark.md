# RedisPal 十万与百万键性能测试报告

测试日期 2026-11-25。通过 Windows 原生 RedisPal 窗口操作真实 Redis，测量默认首批、刷新、继续加载、全部加载、滚动和键名查询。

## 环境

- Windows 11，内部版本 `10.0.26300.0`，Intel Core Ultra 7 155H，约 31.5 GiB 物理内存。测试通过 Playwright 连接应用实际运行的 WebView2，使用 1440 × 900 的 CSS 视口和 100% 应用缩放。
- 当前工作区构建基于 `430b52bc1ebdc31e51dbf9bfe7bc1852636de645`，含当时尚未提交的 UI 改动。用 `production,ardm_desktop_test` 构建以启用本机 WebView2 调试入口，测试 EXE 的 SHA-256 为 `5ec78eafebae379c3c1cd366a7c98a4f771d130abc313f6df532086b49dbe2ba`。
- GitHub 最新发布为 `v0.0.5`，指向同一提交。官方便携包下载后已匹配发布资产 SHA-256，但自动化无法接入它的 WebView2。发布版对照使用标签源码加同一测试构建开关重新编译，SHA-256 为 `427a2120f1960c63474c556d5c0a9559f97037b27ff0bfa7307d54781124578f`。[GitHub v0.0.5](https://github.com/zhanggc2019/RedisPal/releases/tag/v0.0.5)
- Redis 8.10.3，Linux x86-64，单实例，远程直连。写入前实例报告无键，DB15 确认为空。数据使用本次独有的随机前缀和两小时 TTL，桌面应用使用临时 WebView2 profile 和只读连接。

## 数据与 Redis 基线

初次写入使用 Python `random.Random(435899)`，追加使用 `random.Random(535899)`，从 14 种类型、120 个逻辑分组和 96 位随机值中生成数据。键名形如 `<随机前缀>:<分组>:<类型>:<序号>-<随机值截断>`。键值为短串、小集合或少量成员，目的是测键浏览。预置一个唯一键测试精确及模糊查询。以 1,000 键为一批用非事务 Redis pipeline 写入，从 10 万键追加至 100 万键。逐批检查命令回复，每种类型抽一个键核对 `TYPE`，每阶段用 `DBSIZE` 和完整 `SCAN` 校验总数。

## 桌面端测量口径

每个组合使用新进程、临时配置和默认每批 10,000 键。首批从点击连接到 UI 显示 10,000 键，刷新取三次中位数。随后用「加载更多」将 10,000 键增至 20,000，再点击「全部加载」。全部加载耗时从点击到 UI 显示全量计数，并检查分页控件消失。模糊查询使用唯一完整键名走默认子串匹配，精确查询切换「精确匹配」；两者均校验只返回一个键。平铺滚动等两帧再读取实际渲染行索引。

主线程长任务由 `PerformanceObserver` 采集，门槛为 50 ms；最大帧间隔通过 `requestAnimationFrame` 记录。堆内存来自 CDP `Runtime.getHeapUsage` 的操作结束后快照，受 GC 时机影响。桌面端各组合只跑一次全部加载，刷新有三个样本。结果适用于本机、网络和这批短键，不代表并发写入、Redis Cluster、大 Value 编辑或实际生产 P95。

## 代码路径与改进优先级

1. `scan()` 每次收到 Redis 分批结果就向响应式 `state.keys` 追加键。`tree` 计算属性将已加载的完整键数组交给 `keyTree()`，后者重新遍历所有键，建立分组 `Map` 后再转成节点数组。平铺模式也经过 `keyTree()`。固定批大小下，反复处理越来越长的数组，有随批数近似二次增长的风险。约 25 万至 50 万键用了 32 秒，75 万至 100 万键用了 68 秒，与这一机制吻合。尚无 CPU 调用栈采样能拆分树重建、Vue 响应式更新、Wails 序列化和 GC 各自的占比。[分批追加与计算属性](../frontend/src/App.vue#L392) · [键节点构造](../frontend/src/model.js#L99)
2. 虚拟滚动减少挂载的 DOM 行数，但节点构造与可见节点展平发生在视口切片之前。优先在接收新批次时增量更新索引，平铺模式让虚拟列表直接读取键数组。为「全部加载」增加显式进度和取消入口，避免用户在数秒的渲染停顿中反复操作。[虚拟行切片](../frontend/src/KeyTree.vue#L15) · [全部加载入口](../frontend/src/App.vue#L837)
3. 已知完整键名时，精确匹配在 Go 后端执行 `EXISTS`。模糊的唯一键查询使用 `SCAN MATCH`，需要走完整个游标才能确定结束，因此百万库里的搜索等待仍可达约 5 秒。[Redis 后端扫描与精确查询](../internal/redisdesk/browse.go#L75)

## 增量键浏览复测

树形视图在每批返回后仅将新键加入索引。平铺视图直接从键数组取视口所需的行。扫描以完整键身份去重，分页暂存也共享同一个去重集合。刷新或切换数据库后，迟到的扫描结果会被丢弃。

复测沿用同一台 Windows 主机、WebView2、Redis 实例、14 种类型和 10,000 键的默认分页。树形根目录保持折叠。测试 EXE 使用相同构建开关，SHA-256 为 `76e168d48efed508a42404aba6a6851a96a22372a5b7f590e34d6d295638c902`。每种规模和视图各执行一次全部加载。复测使用含界面改动的工作区构建，平铺行高为 28 px。`v0.0.6` 提取键加载改动单独发布，沿用原版 30 px 行高，上述测试 EXE 的结果对应工作区构建。

每次全载后，从树节点的实际键值或平铺组件的键数组中抽取完整键集合。四组的键数和唯一键数均等于目标规模，排序后的 SHA-256 均与独立 Redis `SCAN` 的结果一致。两次平铺均滚到最后一条，百万键全载后仅挂载 35 行 DOM，滚动跳转采样最大耗时 50.6 ms。四轮均未捕获页面 JavaScript 错误。单测另外覆盖重复 `SCAN` 回复、分页暂存、同名叶子、二进制键和迟到的扫描结果。

百万键全载用时在本次测量中分别下降 82.6%（树形）和 68.2%（平铺）。同期纯 Redis `SCAN` 用时为 10.928 s（100 次请求），原测为 18.595 s，端到端差值包含两轮的网络与运行环境波动。百万键下仍有约 0.27–0.33 秒的最长主线程任务。十万键树形的堆快照上升了 14.6 MiB，快照受 GC 时机影响。
